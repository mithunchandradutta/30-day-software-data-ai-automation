## Overview

Day 4's single flat `transactions` table, redesigned into a proper normalized, multi-table financial database — `accounts`, `categories`, `transactions`, `loans`, `investments` — linked with primary keys and foreign keys. This is the schema the real Finance Tracker will eventually run on.

**Today's rule:** don't just create a table. Before every table, ask — is this data being duplicated somewhere? Is this a separate entity, or just an attribute of one that already exists?

## Entities & Relationships

```
accounts (1) ────< transactions >──── (1) categories
   │
   ├──< loans
   └──< investments
```

- `accounts (1) → (many) transactions` — one account has many transactions
- `categories (1) → (many) transactions` — one category labels many transactions
- `accounts (1) → (many) loans` — one account can have many loans
- `accounts (1) → (many) investments` — one account can have many investments

All four relationships here are one-to-many. No many-to-many relationship exists among the core entities yet, so no junction table is in the main schema — `investment_categories` (Learn 2.5) is demonstrated separately in `practice/ex04_relationships.sql` as an optional pattern, not wired into the real schema, because nothing currently needs it.

## Data Integrity Rules

| Rule | Enforced by |
| --- | --- |
| Every transaction must belong to a real account | `account_id INTEGER NOT NULL` + `FOREIGN KEY ... REFERENCES accounts(id)` |
| A category name can't be duplicated | `UNIQUE` constraint on `categories.name` |
| A transaction can't reference an account or category that doesn't exist | Foreign keys + `PRAGMA foreign_keys = ON` (SQLite has this **off** by default — must be enabled per connection) |
| An account with existing transactions can't be silently deleted | No `ON DELETE CASCADE` was added — deleting a referenced account fails with a foreign key error (`RESTRICT`-like default behavior). Decision: losing transaction history by accident is worse than a blocked delete; if an account needs to go away, its transactions should be reassigned or explicitly removed first. |
| `category_id` is nullable, `amount` is nullable | A transaction should still be saveable even without a category ("Uncategorized" case) or with a missing amount (Day 4's real example) — the *row* isn't lost, the gap is just flagged later with `WHERE ... IS NULL`, same as Day 3/4 |

**Deviation from the original spec:** the Day 5 brief defines `amount REAL NOT NULL`. That's dropped here to `amount REAL` (nullable), because Day 4's sample data genuinely has one row with a missing amount, and the migration requirement is "no data lost, row count matches." A `NOT NULL` constraint would have rejected that row outright. Data-quality flagging (`WHERE amount IS NULL`) does the same job SQL-side without silently deleting a row.

## What I Learned

**Database Design**
- A primary key uniquely identifies a row within its own table; a foreign key is a column that points to another table's primary key — that's what turns "two tables" into "one connected system"
- Normalization removes repetition: a category name now lives in exactly one row, so renaming it is a one-row `UPDATE`, not a find-and-replace across every transaction
- One-to-many is the default in real systems (one account, many transactions); many-to-many needs a junction table with a composite primary key
- Indexes speed up lookups on the columns they're built for, but every index also slows down writes and costs storage — indexing everything is not free

**Software Engineering**
- Splitting schema into one file per table (`schema/01_accounts.sql` ... `06_indexes.sql`) made the "System Flow" order (entities → keys → relationships → normalize → indexes) visible in the folder itself
- Migrating without data loss meant relaxing one constraint (`amount NOT NULL` → nullable) rather than silently dropping a row — a trade-off, documented instead of hidden
- `PRAGMA foreign_keys = ON` has to be set per SQLite connection — an easy thing to forget, and foreign keys silently do nothing without it

**Data**
- Re-running Day 4's report against the new schema reproduced the exact same numbers — confirms the redesign didn't change the meaning of the data, only its shape
- The one missing-amount row and the one duplicate row are still visible and still flaggable — normalizing didn't fix or hide the data-quality issues, it just moved them into a cleaner structure

## Future Improvements

- Add a real `ON DELETE CASCADE` / `ON DELETE RESTRICT` decision per foreign key once actual product requirements are clearer
- Support multiple accounts properly (currently every Day 4 row is migrated onto one default `Main Account`)
- Add a `budgets` table (per category, per month) once Day 3/4's category breakdown needs to compare actual vs planned spending
- Revisit `amount NOT NULL` — once the app layer validates input before insert, the database constraint can be tightened back to match the original spec
