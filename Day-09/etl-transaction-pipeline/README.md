# ETL Transaction Pipeline

> Day 9/30 — ETL with Python + SQL | 30 Days of Software Engineering + Data + AI + Business Analytics
> by [Mithun Chandra Dutta](https://github.com/mithunchandradutta)

## Overview

A small, repeatable **Extract → Transform → Load** pipeline that takes a raw,
messy transactions CSV and loads it into a normalized SQLite database
(`accounts`, `categories`, `transactions`) — the same shape of schema as
Day 5, trimmed to just the tables this pipeline actually writes to.

The rule this project is built around: *"it worked" isn't enough — what
happens if you run it twice?*

## ETL Architecture (Extract / Transform / Load)

```
Raw CSV
   |  EXTRACT (extract.py)      -- read only, zero cleaning, zero logic
   v
Untouched raw rows
   |  TRANSFORM (transform.py)  -- type conversion, date parsing,
   |                                missing-value defaults, in-batch dedupe
   v
Cleaned, validated rows
   |  LOAD (load.py)            -- get-or-create accounts/categories,
   |                                skip rows already in the database
   v
accounts / categories / transactions (SQLite)
```

Each step is its own file and its own function — so each can be tested and
debugged on its own, without needing the whole pipeline to reproduce a bug.

## Transformation Rules

| Rule | What happens |
| --- | --- |
| Amount missing or non-numeric (`""`, `"N/A"`, `"abc"`) | Row dropped, counted as `skipped_malformed` |
| Date missing or in an unrecognized format | Row dropped, counted as `skipped_malformed` |
| Date in `DD/MM/YYYY` | Parsed and normalized to `YYYY-MM-DD` (not an error — both formats are accepted) |
| `type` not `income`/`expense` | Row dropped, counted as `skipped_malformed` |
| Category missing/blank | Defaults to `Uncategorized` |
| Account missing/blank | Defaults to `Main Account` |
| Leading/trailing whitespace in description | Trimmed |
| Same `(date, amount, account, description)` twice **in the same file** | Second copy dropped, counted as `skipped_duplicate_in_batch` |

## Duplicate & Re-run Safety Strategy

Two separate duplicate checks, at two separate stages:

1. **In-batch** (Transform): catches the same transaction appearing twice
   *within one raw file* — e.g. an export that accidentally repeated a row.
2. **Against the database** (Load): before every insert, `load.py` checks
   whether a transaction with the same natural key
   (`date + amount + account_id + description`) is already in
   `transactions`. If so, it's skipped.

This second check is what makes the pipeline **idempotent** — running
`run_pipeline.py` on the exact same file twice loads the data once; the
second run loads 0 new rows instead of creating duplicates.

Categories and accounts use a **get-or-create** pattern (`load.py`): if the
name already exists, its `id` is reused; if not, a new row is created and
that `id` is used — this is what actually lets the schema stay normalized
(a raw `category` string becomes a `category_id` foreign key).

## How to Run

```bash
# Run the pipeline (creates data/finance.db from data/raw_transactions.csv)
python run_pipeline.py

# Run it again on purpose -- this is the actual test
python run_pipeline.py

# Run the tests
python test_pipeline.py

# Use a different raw file
python run_pipeline.py data/my_other_export.csv

# Inspect what got loaded
python -c "import sqlite3; c = sqlite3.connect('data/finance.db'); [print(r) for r in c.execute('SELECT * FROM transactions')]"
```

## What I Learned

**Software Engineering**
- Keeping Extract, Transform, and Load as three separate functions made it
  obvious which stage a bug belonged to — a crash in `extract.py` means a
  file/format problem; a wrong count out of `transform.py` means a rule
  problem; duplicate rows after `load.py` means the natural-key check is
  wrong.
- Row-level cleaning (type conversion, trimming, per-row validation)
  belongs in Python; set-level operations (aggregation, grouping across
  many rows) belong in SQL — Day 4's `GROUP BY` queries are a better fit
  for that than a Python loop would be.
- "It ran without errors" and "it's safe to run again" are two different
  claims — only the second one makes a pipeline actually usable in
  automation (this is also exactly the idempotency idea Day 12 builds on).

**Data**
- Deciding what counts as "duplicate" is a judgment call, not a given —
  here it's `date + amount + account + description`; a different natural
  key would make the pipeline more or less strict.
- A missing category isn't an error, but a missing amount is — those two
  "missing" cases needed different handling (default value vs. drop the
  row), and that decision lives entirely in `transform.py`, not scattered
  across the pipeline.

**Business**
- Without re-run safety, every retry (a flaky connection, a scheduled job
  firing twice, a person re-uploading the same file by mistake) silently
  corrupts the numbers any report is built on — no analytics is
  trustworthy on top of a non-idempotent loader.
- This pipeline doesn't care whether the CSV came from Day 4's sample data,
  a bank statement export, or Day 8's API — any source that can be shaped
  into the same raw columns can be pointed at `extract.py` and reused.

## Future Improvements

- Accept a second source type (e.g. Day 8's API JSON output) in `extract.py`
  without changing `transform.py` or `load.py` at all
- Write skipped/malformed rows to a separate `logs/rejected_rows.csv`
  instead of only counting them, so nothing is silently lost
- Move from "full re-extract every run" to an incremental load (only rows
  newer than the last successful run)
- Wrap `load_transactions` in an explicit transaction (`BEGIN`/`COMMIT`)
  so a crash mid-load can't leave accounts/categories created without their
  transactions
