## Overview

Day 3's pandas transaction analyzer, rebuilt with pure SQL. Same data, same business questions (income vs expense, category breakdown, monthly trend, data quality) — this time the query language does the work instead of Python code.

**Today's rule:** whatever `.groupby()` did in pandas, write it in SQL — and understand why the business world still runs on SQL.

## Features

- Loads `data/transactions.csv` into a SQLite database (`data/finance.db`)
- `SELECT` / `WHERE` filtering (comparison operators, `AND`/`OR`/`NOT`, `IN`, `BETWEEN`, `LIKE`, `IS NULL`)
- `ORDER BY` sorting, `GROUP BY` + aggregates (`SUM`, `AVG`, `COUNT`, `MIN`, `MAX`)
- `HAVING` — filtering *after* aggregation
- `INNER JOIN` / `LEFT JOIN` against a `categories` lookup table
- `CASE` for a signed-amount column and High/Medium/Low labels
- A subquery example (above-average expenses)
- Data-quality queries: missing amounts, duplicate rows (`GROUP BY` + `HAVING COUNT(*) > 1`)
- A final report query that reproduces Day 3's exact pandas output
- 6 test cases covering the Day 4 testing table, run against a temporary in-memory database

## Technologies

- SQLite (via Python's built-in `sqlite3` — no server needed)
- Python 3 (only to run the setup script and print the report — the analysis itself is SQL)

## Example Queries

Category totals with `GROUP BY`:

```sql
SELECT category, SUM(amount) AS total_amount
FROM transactions
WHERE type = 'expense'
GROUP BY category
ORDER BY total_amount DESC;
```

Readable labels with `JOIN`:

```sql
SELECT t.date, t.amount, t.category, c.group_type
FROM transactions t
INNER JOIN categories c ON t.category = c.name;
```

Signed amount with `CASE`:

```sql
SELECT date, type, amount,
       CASE WHEN type = 'income' THEN amount ELSE -amount END AS signed_amount
FROM transactions
WHERE amount IS NOT NULL;
```

## Data Quality Handling

Unlike Day 3, the raw CSV is loaded **as-is** into `finance.db` — the missing amount and the duplicate row are *not* removed before loading. Cleaning happens inside the SQL query itself:

| Problem | SQL technique | Why |
| --- | --- | --- |
| Missing amount | `WHERE amount IS NOT NULL` | `amount = NULL` never matches in SQL — `IS NULL` / `IS NOT NULL` are required |
| Duplicate rows (same date + amount + category) | `GROUP BY date, amount, category HAVING COUNT(*) > 1` to detect; `WHERE id IN (SELECT MIN(id) ... GROUP BY ...)` to keep only the first copy | Same fingerprint idea as Day 3, expressed as a query instead of a pandas function |
| Category with no matching lookup row | `LEFT JOIN` keeps the row with `NULL`; `INNER JOIN` drops it | The report decides which is correct — "show everything" vs "only confirmed categories" |

`queries/06_final_report.sql` builds a `deduped` CTE (`WITH ...`) once and reuses it for totals, breakdown, top/lowest expense and the monthly trend — the same cleaned view every part of the report reads from.

## What I Learned

**SQL**
- Execution order is `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY` — not the order it's typed in
- `WHERE` filters rows before grouping; `HAVING` filters groups after aggregation
- `INNER JOIN` drops unmatched rows, `LEFT JOIN` keeps them with `NULL`
- `CASE WHEN ... THEN ... ELSE ... END` builds a derived column inline
- A subquery can feed a `WHERE` condition (e.g. compare each row to an average)
- SQL is declarative — you say *what* you want; pandas is closer to saying *how*, step by step

**Software engineering**
- Splitting queries by purpose (schema, filter, group, join, flags, report) instead of one giant script
- A CTE (`WITH`) lets several report sections share the same "cleaned" definition instead of repeating logic
- Testing SQL against a throwaway in-memory database keeps tests from touching real data

**Data**
- Recomputed the exact same numbers as Day 3's pandas report — confirms the pandas cleaning logic and the SQL cleaning logic agree
- `GROUP BY` + `HAVING COUNT(*) > 1` found the same one duplicate row and one missing amount as pandas did
- Grouping is easier to read in SQL for simple totals; the `CASE`-based signed amount and the CTE-based dedup took more thought than the pandas equivalent
